01 — Overview

One process, one tenant, one account

The server signs in to Ivanti as a single API user. Everything it does executes as that account, like a call-centre operator working on someone's behalf — the person an operation is for is recorded in the record's Customer field, never inferred from who is talking.

This is the rule that catches people out. Anything Ivanti resolves "for the current user" — a saved search called “My Incidents”, an approval queue, an assignment — answers for the service account, not for whoever is chatting. Call act_as once per conversation to say who you are helping. In enduser mode nothing returns a record until you do.

Unless you give it a ConfigDB key, and then it really is them. With IVANTI_CONFIG_URL and IVANTI_CENTRAL_CONFIG_API_KEY set, act_as opens an Ivanti session as that person and Ivanti applies their own access — a self-service role reads 0 of the 551 incidents an analyst reads, through the identical request, and a ticket they raise carries their name in CreatedBy rather than the service account’s.

Every surface follows the person: records, forms, pick lists, quick actions, and a service request with a file attached — measured, the request and its attachment both carry the person’s name in CreatedBy. What stays on the service account does so because it describes the tenant rather than the person: the schema, the admin catalog, the person directory. And the server’s own checks still run — the object gate and the ownership rules — because a second, independent line is worth keeping even where Ivanti draws the first.

If the session cannot be opened, the call is refused rather than quietly answered as the service account: being told the wrong person’s data is yours is worse than being told nothing.

Three Ivanti surfaces, two credentials

The server talks to Ivanti three ways and the authentication is not uniform, which is why the connection is probed at startup rather than configured.

SurfaceCredentialUsed for
OData / RESTAuthorization: rest_api_key=…Records, metadata, attachments
ASMX servicesSID cookie + CSRF tokenForms, picklists, quick actions, service requests
/HEAT/AdminUI/Admin-rights keyThe complete 1,324-object catalogOptional — every feature built on it degrades instead of breaking

The base path is probed too: tenants serve the API under /HEAT or at the root, and startup walks both against $metadata, keeping whichever answers with a CSDL document. A tenant that answers neither fails the startup rather than deferring the error to the first tool call.

02 — Quick start

Running in under a minute

Pick the shape that matches how the model will reach the server. Nothing here compiles anything: the image, the chart and the tarball are published builds.

A. Desktop client over stdio

The default. No socket, no AUTH_MODE — the credential is the ability to run the process.

# .env
STDIO_TRANSPORT_ON=true
IVANTI_BASE_URL=https://your-tenant.example.com
IVANTI_API_KEY=your-key

# then, whichever you have:
docker run -i --rm --env-file .env tyrunas/ivanti-mcp:0.1.1
node /opt/ivanti-mcp/dist/index.js

B. One host over HTTP

Loopback only. MCP_BIND defaults to 127.0.0.1 precisely so that exposing the server is a second, deliberate act.

STDIO_TRANSPORT_ON=false
HTTP_TRANSPORT_ON=true
AUTH_MODE=none
MCP_BIND=127.0.0.1
MCP_PUBLIC_URL=http://127.0.0.1:3000/mcp
TRUSTED_ORIGINS=http://localhost

C. Container behind a token

The published image is multi-arch, so the same tag runs on both architectures.

docker pull tyrunas/ivanti-mcp:0.1.1
docker run --rm -p 3000:3000 --env-file .env \
  -e MCP_BIND=0.0.0.0 \
  -v /run/secrets:/run/secrets:ro \
  --read-only --cap-drop ALL --security-opt no-new-privileges \
  tyrunas/ivanti-mcp:0.1.1
03 — Deploy

Three shapes, one build

A tagged release publishes a multi-arch image, a Helm chart and a self-contained tarball from the same commit — so whichever shape you pick, it is the same code, and the version it reports is the version you tagged.

ShapeRuns asTransportGet it with
Plain Node hosta systemd servicestdio or HTTPthe release tarballNode 22 and nothing else — no compiler, no package manager, no registry
Containerdocker run or composeeithertyrunas/ivanti-mcpmulti-arch, distroless, signed
Kubernetesa DeploymentHTTP onlyoci://ghcr.io/tyrunasj/charts/ivanti-mcpa Helm chart over that same image

Two rules hold whatever the shape. One instance is one tenant — staging, UAT and production are three deployments, not three tenants in one process. And one instance is one audience: full and enduser are different products, and mixing them is how an employee ends up holding an analyst's tool surface.

A. Plain Node host

The tarball carries its own production dependencies as real directories, rather than the package manager's default layout of symlinks into a content-addressed store — that layout does not survive being moved to another machine, so the release flattens it rather than shipping a lockfile and hoping.

curl -fsSLO https://github.com/tyrunasj/ivanti-mcp-standalone/releases/download/v0.1.1/ivanti-mcp-0.1.1.tar.gz
sudo useradd --system --home /opt/ivanti-mcp --shell /usr/sbin/nologin ivanti-mcp
sudo install -d -o ivanti-mcp -g ivanti-mcp /opt/ivanti-mcp /etc/ivanti-mcp
sudo tar xzf ivanti-mcp-0.1.1.tar.gz --strip-components=1 -C /opt/ivanti-mcp
sudo chown -R ivanti-mcp:ivanti-mcp /opt/ivanti-mcp

# Configuration, not the unit file: `systemctl cat` shows a unit to everyone.
sudo install -m 0640 -o root -g ivanti-mcp .env /etc/ivanti-mcp/env
sudo install -m 0644 deploy/systemd/ivanti-mcp.service /etc/systemd/system/
sudo systemctl enable --now ivanti-mcp

Set STDIO_TRANSPORT_ON=false for a service. systemd hands the process a stdin, and the stdio transport will sit on it indefinitely waiting for a JSON-RPC stream that is never coming. The service looks healthy and answers nothing.

The unit mirrors the container's posture — unprivileged, read-only filesystem, no capabilities, syscall-filtered. Two things it deliberately does not do:

  • MemoryDenyWriteExecute is not set. Node's JIT maps pages writable and then executable, so under that directive the process dies in a way that reads as a segfault rather than as a policy denial.
  • RestartPreventExitStatus=78 is set. A configuration error will still be a configuration error in five seconds; restarting into it just fills the journal.

B. Container

docker pull tyrunas/ivanti-mcp:0.1.1

Multi-arch (linux/amd64, linux/arm64), 55.4 MB to pull on amd64 and 55.0 MB on arm64 — measured on the published manifest, of which 52.6 MB is the distroless Node base — uid 65532. Three stages: build → production dependencies → a distroless runtime (gcr.io/distroless/nodejs22-debian12) with no shell and no package manager — nothing to exec into and nothing to install from, which is the point. It runs under --read-only with all capabilities dropped and writes nothing to disk.

Tags: 1.2.3, 1.2, 1 and latest for a final release; a prerelease publishes its exact version only, so nobody pulls a release candidate by accident. Every main build also pushes main and sha-<short>. Pin a digest in production.

Images are signed with cosign, keylessly — there is no key to rotate or leak:

cosign verify tyrunas/ivanti-mcp:0.1.1 \
  --certificate-identity-regexp='^https://github.com/tyrunasj/ivanti-mcp-standalone/' \
  --certificate-oidc-issuer=https://token.actions.githubusercontent.com

C. Kubernetes

helm install ivanti-mcp oci://ghcr.io/tyrunasj/charts/ivanti-mcp \
  --version 0.1.1 --namespace ivanti --create-namespace \
  --set server.publicUrl=https://mcp.example.com/mcp \

  --set ivanti.baseUrl=https://your-tenant.example.com \
  --set secrets.existingSecret=ivanti-mcp-secrets

The chart forces STDIO_TRANSPORT_ON=false, HTTP_TRANSPORT_ON=true and MCP_BIND=0.0.0.0. None of those is a choice in a pod, so none of them is a value you can set.

It refuses to render rather than letting you find out later. The server exits 78 on a bad configuration; the chart moves that failure earlier still, to helm install.

RefusedBecause

One replica, and that is not laziness. HTTP sessions live in memory — one McpServer per Mcp-Session-Id, created on initialize. Scale to two and roughly half of every conversation's requests land on a pod that has never heard of that session. It presents as intermittent client bugs, which is the worst way for it to present. More replicas need consistent hashing on that header at the ingress: --set replicaCount=3 --set sessionAffinity.enabled=true, which adds the nginx upstream-hash-by annotation. Confirm your controller honours it — the chart cannot.

Secrets come from secrets.existingSecret, keys ivanti-api-key and — for bearer auth — bearer-token. They mount at /run/secrets with defaultMode: 0400, and the pod sets fsGroup: 65532 so the image's own user can read them: the ownership trap below, closed by default. secrets.create=true exists for development and puts the values in Helm history, where helm get values will show them.

Probes are plain httpGet against /health, which is unauthenticated and always answers 200 — also the only option, since a distroless image has no curl. The startup probe is generous (two minutes) because boot does real network work: it walks the tenant's base paths against $metadata and opens the ASMX session.

How much memory it needs

Measured rather than modelled: sessions were opened against a running server and held open, and resident memory read from the process after each hundred. The relationship is linear — 96 MB with nothing connected, plus roughly 134 KB per concurrent session.

The per-session figure falls as the count rises, because the fixed cost — the tool definitions, their zod schemas, the metadata catalog — is paid once and shared by reference. Only the per-connection McpServer and its transport are per session, which is exactly why selectTools() runs at startup and never per connection.

Two things this chart leaves out. A session that is working allocates on top of this, transiently: one page of twenty-five full records measured 187,278 characters, which is why rows default to a compact field set. And MCP_MAX_SESSIONS defaults to 100 — reaching the right-hand end of this chart means raising it deliberately, and the server answers 503 past the ceiling rather than growing without bound.

The chart's defaults are sized accordingly: a 192Mi request comfortably holds the default ceiling of 100, and the 512Mi limit still has headroom past 1,000. Idle memory dominates until around 700 sessions — below that you are paying for Node and the catalog, not for users.

Four things that bite, in every shape

  • The tenant hostname must resolve where the process runs, which is a different question from whether it resolves on the machine you are typing on. Split-horizon DNS has been observed handing a container a LAN address it could not route to, so every startup probe failed as a connection error. Pin it with --add-host, compose's extra_hosts, or the chart's hostAliases.
  • MCP_BIND must be 0.0.0.0 inside a container or a pod. Loopback there is the container's own, and the published port carries nothing. The default is 127.0.0.1 precisely so that exposing the server is a second, deliberate act.
  • package.json ships next to dist/. The server reads its version from the manifest at startup and refuses to start without it — an unidentifiable deployment is worse than one that fails loudly. A container that starts and then exits is usually this.
  • The health check is a Node script, because a distroless image has no shell and no curl. It exits 0 when HTTP_TRANSPORT_ON is off — a stdio deployment serves no HTTP, and calling that unhealthy would be worse than not checking.

Secrets

Any secret takes a _FILE suffix instead of a value: BEARER_TOKEN_FILE, IVANTI_API_KEY_FILE. Setting both forms is an error rather than a precedence question. Prefer files everywhere that is not a laptop — docker inspect, kubectl describe pod and /proc/<pid>/environ all show the environment; a mounted secret shows a path.

A mounted file keeps the ownership it has on the host, and the image runs as uid 65532. A secret written by your own account with mode 600 is unreadable inside the container, and the server exits 78 with EACCES — which reads like a missing file rather than a permission. Fix: chown 65532:65532 secrets/* && chmod 600 secrets/*. The Helm chart sets fsGroup and does not have this problem.

Cutting a release

Tag and push. The workflow refuses a tag that disagrees with package.json, because the server reports its version from the manifest — a mismatch would ship an image that misreports what it is.

# bump package.json first, then:
git tag v0.2.0 && git push origin v0.2.0

One tag builds the image for both architectures, signs it, packages the chart, builds the tarball and opens the GitHub release — from one commit, so the three shapes cannot drift apart.

06 — OAuth providers

The only door that carries a verified identity

Under bearer, everyone holding the token is the same anonymous caller. Under oauth the token says who, and the person a conversation is helping stops being a claim it makes about itself. Three settings usually do it; the difficulty is entirely in what each provider decides to put in the token.

The audience is not your URL, and this is the commonest reason OAuth “doesn’t work” here. The spec has clients send resource=<your MCP URL>, which reads as though aud will then contain that URL. No mainstream provider works that way. So OAUTH_AUDIENCE is set independently of MCP_PUBLIC_URL: it is a comma-separated list, the token's own aud may itself be an array, and a token is accepted when the two sets intersect. A verifier written to the spec's literal wording rejects every real token.

ProviderWhat actually lands in audThe thing that will catch you
Entra IDdepends on the token versionv2: the API's client-id GUID · v1: the App ID URICannot be tested against localhost at all — see below
Zitadelthe client idToken type defaults to Bearer, which is opaque. Set Auth Token Type: JWT on the application
Oktathe authorization server's AudienceUse a custom authorization server — the org one issues opaque tokens
Keycloakthe client idDefault aud is account. Add an Audience mapper on the dedicated client scope
Auth0the API identifierOpaque unless a Default Audience is set tenant-side; its issuer ends in a trailing slash
JumpCloudthe client idNo dynamic registration — pre-register and pin the client id
Google—Not usable. Access tokens are opaque and there is no introspection endpoint

Nearly every failure is one of two shapes. An opaque token — the server answers “Access token is opaque, not a JWT”, and a JWKS verifier genuinely cannot inspect one: there is no header and no signature to check. That is always a provider setting, never a server one. Or the wrong audience, where the token is perfectly valid and simply was not minted for you. Decode it and read its real aud before changing anything else.

Entra is the exception, in four separate ways

It is the majority deployment and the one that behaves least like the others. None of these is something you can configure your way around.

  • Its audience depends on the token version you asked for. With requestedAccessTokenVersion: 2 the aud is the API's client id — a bare GUID. On v1.0 tokens it is the Application ID URI, api://<appId>. Both are correct; they are different strings, and putting the wrong one in OAUTH_AUDIENCE produces a valid token that this server refuses. Check the registration before assuming which you have.
  • It cannot be tested against a local server. Entra requires the resource to be a registered Application ID URI, and a conforming client separately insists the resource equals the endpoint it connected to. http://localhost:3000/mcp can never satisfy both — deploy to a public HTTPS name on a verified domain first, and then the App ID URI, MCP_PUBLIC_URL and the endpoint are one identical string. The api:// scheme takes a GUID that must match the app or tenant id, or an arbitrary string that must sit on a verified custom domain or the tenant's initial domain; api://<appId> is the recommended form.
  • Discovery only resolves on the third probe. Its issuer carries a path (…/{tenant}/v2.0), and the two path-insertion forms answer 404 — only appending /.well-known/openid-configuration to the issuer works. An implementation that tries fewer candidates cannot reach Entra at all.
  • It publishes no code_challenge_methods_supported — alone among ten providers measured here — while supporting PKCE S256 in practice. The spec says a client MUST refuse to proceed when that field is absent, so whether a given client tolerates it is decided on the client side and cannot be fixed from this end.

One app registration is enough: it can expose the API and act as the client. And if Custom domain names refuses to verify while your DNS is demonstrably correct, the domain is almost certainly claimed by another Microsoft tenant — often an unmanaged one created when somebody signed up for a free service using an address at that domain. That is a takeover case, not a DNS problem.

What to set

Discovery is the default: give it the issuer and the authorization-server metadata is fetched at startup, in the spec's probe order.

AUTH_MODE=oauth
OAUTH_ISSUER=https://login.microsoftonline.com/<tenant-id>/v2.0
OAUTH_AUDIENCE=<the API's client id, for a v2.0 token>

# Optional. Setting it skips discovery entirely — which is what you want when a
# provider publishes its metadata somewhere the spec's probe order does not look.
OAUTH_JWKS_URI=https://login.microsoftonline.com/<tenant-id>/discovery/v2.0/keys

# Which claim names the person. Entra sends preferred_username or upn, most
# others send email, and sub is opaque. Unset, a probe order is used.
OAUTH_IDENTITY_CLAIM=preferred_username

Assume the provider does not support dynamic client registration. Half of those surveyed do not, so a pre-registered client with a pinned client id is the documented path. Pinning also closes a Zitadel-specific trap: registration there creates a fresh application each time, which inherits the instance default of Bearer — so flipping one application to JWT lasts exactly until the next re-authentication makes another.

The redirect URI is not ours. It is where the provider sends the user back after login, so it belongs to the client application; this server neither hosts one nor ever sees it. MCP_PUBLIC_URL is always this server's own externally visible address. Confusing the two is the second-commonest setup failure — and a loopback redirect is not a “dev mode”, it is simply what a client running on somebody's own machine legitimately uses.

This server verifies tokens with JWKS and nothing else. It never mints a token, serves no registration endpoint and hosts no client metadata document: registration is strictly between the client and the authorization server. Token introspection is deliberately deferred rather than forgotten — across ten providers measured, jwks_uri was universal while introspection was absent on four, Entra included.

07 — Capability tiers

What the credential can reach

Probed once at startup, because tools are selected once. Each rung only ever adds — a lower tier is not a failure, and refusing to start would punish exactly the customers who cannot hand an MCP server an admin key.

1

Every read tool, and ~194 objects discovered from the metadata graphs.
2
session+ the ASMX handshake
The identity, the role's own workspaces, picklist values, quick actions and the service catalog. Most tools need this.
3
admin+ the admin console
The complete catalog — 1,324 objects with display names and descriptions, against 194 from metadata and 24 from workspaces.

get_pick_list_values is the first tool the tier actually gates: it needs a create form, which OData cannot see.

Testing a degraded tier needs IVANTI_MAX_TIER. Ivanti's AuthenticateTenantAPIKey ignores its own role argument — an admin account asking for SelfService still answers Admin — so the lower paths cannot be exercised by asking for a lesser role. Cap the server instead.

08 — Audience modes

full and enduser are different products

Chosen at startup; never mix audiences in one instance. Tool narrowing happens at registration, never inside a handler — an unregistered tool never appears in tools/list, so the model cannot call it at all.

 fullenduser
AudienceIT staffEmployees
Tools4034 no assigned-work, saved searches, preview-delete or link/unlink
Business ObjectsAll the credential can seeENDUSER_BUSINESS_OBJECTS a gate, not a hint — empty means none
act_asA preference: decides who “my” meansA gate: nothing returns a record until it resolves
RecordsAnyone's — an analyst works other people's ticketsOwn records only; someone else's is refused

Name quick actions, never pattern-match them. They are the tenant's own text and a tenant renames them freely. On an admin key a stock incident offers 104 actions, including escalation notifications and analyst-only composites — read them off list_quick_actions in full mode and copy the handful an end user should have.

A shared token grants its whole tool surface to everyone who can use it. Size the audience to the surface: pair a widely-shared bearer token with MCP_MODE=enduser.

12 — What a session costs

Where the context window goes

Every figure below is a character count read off this running server, not an estimate. Token columns divide by four, which is the usual rough ratio for English and a little pessimistic for JSON — treat the characters as exact and the tokens as indicative.

The standing cost, paid once per session

This arrives before the model has asked anything. It is re-sent on every new conversation, which is what makes it worth measuring rather than guessing.

WhatCharacters≈ tokensWhen
instructionswho the server signs in as, and what that means1,465~370at connect

The manifest is nearly full, and the build enforces it. Descriptions total 37,625 characters against a 38,000 budget — 375 characters of headroom. Per tool the cap is 2,000, because clients truncate silently from the END and the last paragraph is where the warnings live; run_quick_action sits at 1,948. The next paragraph anyone adds fails the build, which is the intended behaviour: the fix is to move material into a reference resource, never to raise the number, because text past a client's cap is not reaching the model at all.

On demand — paid only if something reads it

Reference material lives in MCP resources rather than in descriptions precisely so it is not part of that standing cost. All six together are smaller than the tool descriptions alone, and most sessions fetch none of them.

The split is a rule, not a preference: a description carries what is dangerous not to know, a resource carries what is expensive to repeat. Anything whose absence would actively mislead stays in the description, because a resource is a pull and plenty of clients never pull one.

Per call — the part that can ruin a window

Response size dwarfs everything above, and it is the one term you control per call.

A default page of twenty-five full records measured 187,278 characters — roughly 47,000 tokens, two and a half times the entire manifest, from a single list_records. A full Ivanti record is about 180 fields. That is why rows default to a compact field set and the response tells you which one it used; asking for fields explicitly is cheaper still.

Waste — measured by driving the manifest, not reading it

Six agents per run worked realistic scenarios with no access to the source, so anything they got wrong was a manifest defect rather than a coding mistake. Calls were then classified as useful or wasted, separating the agent's own errors from the manifest's.

CallsWastedShare
First runbefore any of it was fixed~170~72~42%
Fifth runafter five rounds of fixes58~8~14%

Two thirds of the calls disappeared. A wasted call costs twice — the request and a useless response that stays in the window — so manifest quality is a token concern before it is a correctness one. The exercise found two access holes, a wrong error gloss two agents hit independently, and the most dangerous sentence in the manifest: “an empty result genuinely means no match”, disproved by a keyword search that found none of 344 matching files.

One honest caveat about those runs. The agents were meant to see nothing but the tool manifest, and the harness injected the repository's own agent-orientation document into each of them regardless. The defects they found are real — they were reproduced and fixed — but the waste percentages are a floor, not a clean measurement.

13 — Limits and roadmap

What it will not do, and what is only deferred

Three different things get confused with each other: a limit you must design around, a decision waiting on a condition, and a door deliberately closed. They are separated here, and the closed ones carry their reason — a refusal without one is indistinguishable from an oversight.

Known limits

Opaque access tokens are refusedVerification is JWKS only. Google is unusable — its access tokens are opaque and it publishes no introspection endpoint. Zitadel, Okta and Auth0 each issue opaque tokens until a provider-side setting is changed; see section 06.

HTTP sessions live in memoryOne replica unless the ingress hashes Mcp-Session-Id consistently. Scale without that and roughly half of every conversation's requests reach a pod that has never heard of the session — which presents as intermittent client bugs.
Protocol 2025-11-25What the SDK implements. Requirements from a newer revision are not available here yet, whatever the specification says.
Attachments are capped at 2 MBUploads travel as base64 in a tool call, so the bytes cross the model's context twice. A larger file is refused rather than silently truncated.
The tool manifest is nearly full375 characters of headroom against a 38,000 budget, and 2,000 per description. The next paragraph added fails the build on purpose — clients truncate silently from the end, so text past the cap never reaches the model and a bigger number would only hide that.

Deferred, with the condition that would change it

Neither of these is abandoned. Each is written down with what would have to become true.

Token introspection (RFC 7662). Measured across ten providers: jwks_uri is universal, introspection is absent on four — Entra included — so it cannot be the general path and cannot rescue the majority. It would also cost a round trip to the identity provider on every request and make the server unusable whenever that provider is unreachable; caching fixes the latency and trades away instant revocation, which was the reason to want it.

Revisit if a customer's provider issues opaque tokens and their policy forbids switching to JWT; or a provider appears with no jwks_uri at all; or instant revocation becomes a stated requirement rather than a preference. It is cheap when that happens — everything downstream depends on a single verifier type, so a second implementation is purely additive and enables itself from configuration.

How enduser answers “my records” — settled. This was open between a read-back scoped to the session and a fully identity-backed query. It is now the second, where the tenant allows it: given IVANTI_CONFIG_URL and IVANTI_CENTRAL_CONFIG_API_KEY, act_as opens a real Ivanti session as that person and Ivanti applies their own access to it. Measured on a live tenant: a self-service role reads 0 of the 551 incidents an analyst reads, through the identical request. Set neither and the previous behaviour is unchanged — the server’s own ownership checks run either way, and are not relaxed by this.

A possible shape for the rest of the year

This is an estimate, not a commitment. Durations are read off the code — how much has to change and what it touches — and the calendar assumes one developer at roughly half time. Change that assumption and every bar moves. Nothing here is promised to anyone.

The order is not arbitrary. September is release hygiene, because the manifest is 375 characters from failing the build — moving material into reference resources is close to forced rather than optional. The shared session store is the pivot: it is the largest single item and it is what removes the one-replica guard, so metrics and rate limiting are worth less before it lands — you would be observing and throttling a single pod. December is deliberately light, and the clean re-run of the blind-agent exercise is budgeted in weeks rather than days because it needs a harness that does not inject this repository's own context into the agents; the previous attempt failed at exactly that.

Two items carry a constraint that makes them larger than they look. Readiness cannot be bolted onto /health: that endpoint is anonymous and always answers 200 by design, because a probe that flaps when a token expires would restart a healthy container. A real readiness signal is a second path. Metrics inherit the same rule — resource figures handed to an anonymous caller turn blind probing into a guided attack, so the endpoint has to be authenticated. And TypeScript 7 is absent from the chart because it is blocked on someone else's release: type-aware linting still declares a ceiling below it.

Decided against

These are not gaps. Each was considered, tested where testable, and turned down for a reason that still holds.

Not plannedBecause
Several tenants in one processThe process boundary is a better fence than code: a tenant cannot leak across a boundary that does not exist in the first place. It would also put a tenant argument on all forty-one tools, where forgetting it once is a silent write to the wrong tenant. Staging, UAT and production are three deployments. Revisit if per-tenant deployments ever cost more than the isolation is worth — the opposite of the handful-of-environments case this was decided against.
Per-user Ivanti API keysNot provisionable at tens of thousands of employees.
A read-only gate for productionProduction is where the work happens. A switch that makes the useful deployment useless gets turned off.
A roles and permissions system in the serverOnly oauth could feed it a real identity, and the MCP annotations plus the client's own approval flow already cover the ground.
Ivanti impersonationUnnecessary once every operation runs as one account and the person it is for is recorded in the record's own Customer field.
Handing service-request staging ids to the callerA staging id is one-shot, and submitting it twice moves the file off the first request rather than copying it. Staging happens inside the submit, so an id that never leaves the server cannot be misused — the footgun is designed out rather than documented.
Voting through “Approve My Vote”Ivanti resolves “my” from the signed-in session, so it would record this server's service account as the decision-maker, and on an admin key its override sibling bypasses the real approver entirely. Votes are cast on the approver's own vote row instead.
Voting by setting a vote row's statusMeasured: it stores the status, overwrites the recorded voter with the session account, and leaves the approval pending. The workflow never fires, so it is a vote that counts for nothing.
