01 — Overview

One process, one tenant

The server signs in to one Ivanti tenant with one API key. Every conversation starts with act_as, naming the person being helped; what happens next depends on whether impersonation is set up.

  • Without impersonation, everything runs as the API key’s account, like a call-centre operator working on someone’s behalf. The person an operation is for is recorded in the record’s Customer field, never inferred from who is talking.
  • With impersonation, act_as opens an Ivanti session as that person: Ivanti applies their own access, and what they create carries their name. See Impersonation.
02 — Quick start

Running in under a minute

Pick the shape that matches how the model will reach the server. Nothing here compiles anything: the image, the chart and the tarball are published builds.

A. Desktop client over stdio

The default. No socket, no AUTH_MODE — the credential is the ability to run the process.

# .env
STDIO_TRANSPORT_ON=true
IVANTI_BASE_URL=https://your-tenant.example.com
IVANTI_API_KEY=your-key

# then, whichever you have:
docker run -i --rm --env-file .env tyrunas/ivanti-mcp:0.2.5
node /opt/ivanti-mcp/dist/index.js
node "C:\Program Files\ivanti-mcp\dist\index.js"

B. One host over HTTP

Loopback only. MCP_BIND defaults to 127.0.0.1 precisely so that exposing the server is a second, deliberate act.

STDIO_TRANSPORT_ON=false
HTTP_TRANSPORT_ON=true
AUTH_MODE=none
MCP_BIND=127.0.0.1
MCP_PUBLIC_URL=http://127.0.0.1:3000/mcp
TRUSTED_ORIGINS=http://localhost

C. Container behind a token

The published image is multi-arch, so the same tag runs on both architectures.

docker pull tyrunas/ivanti-mcp:0.2.5
docker run --rm -p 127.0.0.1:3000:3000 --env-file .env \
  -e MCP_BIND=0.0.0.0 \
  -v /run/secrets:/run/secrets:ro \
  --read-only --cap-drop ALL --security-opt no-new-privileges \
  tyrunas/ivanti-mcp:0.2.5

Two rules hold whatever the shape. One instance is one tenant — staging, UAT and production are three deployments, not three tenants in one process. And one instance is one audience: full and enduser are different products, and mixing them is how an employee ends up holding an analyst's tool surface.

How every shape starts

Open the configurator, answer its six questions, and pick where it runs. Download each file it shows into one empty folder — the steps below call it the folder. Browsers may save .env as env; rename it back. Then follow the steps for your shape.

A. Linux host

A systemd service running the release tarball on Node 22 or later.

  1. Configurator: pick Linux, then download .env and ivanti-mcp.service into the folder.
  2. Edit .env: set IVANTI_BASE_URL to your tenant, and — for HTTP — MCP_PUBLIC_URL and TRUSTED_ORIGINS.
  3. Install the release, from the folder: 
    curl -fsSLO https://github.com/tyrunasj/ivanti-mcp-standalone/releases/download/v0.2.5/ivanti-mcp-0.2.5.tar.gz
sudo useradd --system --home /opt/ivanti-mcp --shell /usr/sbin/nologin ivanti-mcp
sudo install -d -o ivanti-mcp -g ivanti-mcp /opt/ivanti-mcp
sudo tar xzf ivanti-mcp-0.2.5.tar.gz --strip-components=1 -C /opt/ivanti-mcp
  4. Install the settings and secrets. They are readable by root and the service only; skip the secret lines if you chose Environment for secrets. 
    sudo install -d -m 0750 -o root -g ivanti-mcp /etc/ivanti-mcp /etc/ivanti-mcp/secrets
sudo install -m 0640 -o root -g ivanti-mcp .env /etc/ivanti-mcp/env
read -rs -p 'Ivanti API key: ' k; printf %s "$k" | sudo install -m 0640 -o root -g ivanti-mcp /dev/stdin /etc/ivanti-mcp/secrets/ivanti-api-key; unset k
# bearer only — give this token to your clients
openssl rand -hex 32 | tr -d '\n' | sudo install -m 0640 -o root -g ivanti-mcp /dev/stdin /etc/ivanti-mcp/secrets/bearer-token
  5. Install and start the service: 
    sudo install -m 0644 ivanti-mcp.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now ivanti-mcp
  6. Check it: 
    systemctl status ivanti-mcp
journalctl -u ivanti-mcp -n 20          # the startup lines list every tool the key reaches
curl -s http://127.0.0.1:3000/health    # {"status":"ok"} — HTTP only

The unit runs unprivileged, with a read-only filesystem, no capabilities and a syscall filter. It does not restart on exit 78: a configuration error will still be one in five seconds, so read the journal instead.

B. Container

The published image, run with Docker or Docker Compose.

  1. Configurator: pick Docker, then download .env and compose.yaml into the folder — or docker-run.sh if you do not use Compose.
  2. Edit .env: set IVANTI_BASE_URL to your tenant, and — for HTTP — MCP_PUBLIC_URL and TRUSTED_ORIGINS.
  3. Add the secrets in a secrets folder beside them, owned by the image’s user (uid 65532). Skip this if you chose Environment for secrets. 
    mkdir secrets
read -rs -p 'Ivanti API key: ' k; printf %s "$k" > secrets/ivanti-api-key; unset k
openssl rand -hex 32 | tr -d '\n' > secrets/bearer-token    # bearer only — give it to your clients
sudo chown 65532:65532 secrets/* && sudo chmod 600 secrets/*
  4. Start it from the folder — docker compose up -d, or the commands in docker-run.sh.
  5. Check it: 
    docker compose ps
docker compose logs --tail 20           # the startup lines list every tool the key reaches
curl -s http://127.0.0.1:3000/health    # {"status":"ok"} — HTTP only

The image is multi-arch (linux/amd64, linux/arm64), about 55 MB to pull, distroless — no shell, no package manager — and runs as uid 65532. Final releases are tagged 1.2.3, 1.2, 1 and latest; pin a digest in production. To verify the signature before running it:

cosign verify tyrunas/ivanti-mcp:0.2.5 \
  --certificate-identity='https://github.com/tyrunasj/ivanti-mcp-standalone/.github/workflows/release.yml@refs/heads/main' \
  --certificate-oidc-issuer=https://token.actions.githubusercontent.com

C. Kubernetes

A Helm chart over the same image. It is HTTP-only and runs one replica.

  1. Configurator: pick Kubernetes, then download values.yaml and helm-install.sh into the folder.
  2. Edit values.yaml: server.publicUrl, server.trustedOrigins, ivanti.baseUrl, and the ingress host if you publish it.
  3. Add the secrets in a secrets folder beside them: 
    mkdir secrets
read -rs -p 'Ivanti API key: ' k; printf %s "$k" > secrets/ivanti-api-key; unset k
openssl rand -hex 32 | tr -d '\n' > secrets/bearer-token    # bearer only — give it to your clients
  4. Run helm-install.sh from the folder, a block at a time: it creates the namespace and the Secret, installs the chart, and checks the rollout and /health. Its last blocks — upgrade, restart — are for later.
  5. Remove the local copies once the Secret exists: rm -r secrets. The Secret holds them now.

The chart refuses to render rather than letting you find out later. The server exits 78 on a bad configuration; the chart moves that failure earlier still, to helm install.

One replica, and that is not laziness. HTTP sessions live in the process’s memory, created on initialize. Scale to two and roughly half of every conversation's requests land on a pod that has never heard of that session. It presents as intermittent client bugs, which is the worst way for it to present. Hashing that header at the ingress does not help: initialize carries no session id, so whichever pod answers it mints one, and a hash of that id reaches the same pod only by chance. The chart refuses replicaCount above 1, and a rollout ends every conversation.

Secrets come from secrets.existingSecret, keys ivanti-api-key and — for bearer auth — bearer-token. They mount at /run/secrets with defaultMode: 0400, and the pod sets fsGroup: 65532 so the image's own user can read them: the ownership trap below, closed by default. secrets.create=true exists for development and puts the values in Helm history, where helm get values will show them. Keys are read once, at startup, and the chart cannot see an existing Secret change: after rotating one, change rolloutToken in the same commit, or run kubectl rollout restart.

A NetworkPolicy admits traffic to the pod from networkPolicy.from only — by default, pods in the release's own namespace. It is on by default exactly when authMode is none (enabled: auto), where nothing else stands in front of the tool surface; with an ingress, add the controller's namespace. It is inert unless the CNI enforces NetworkPolicy, and kubectl port-forward is not subject to it.

Probes are plain httpGet against /health, which is unauthenticated and always answers 200 — also the only option, since a distroless image has no curl. The startup probe is generous (two minutes) because boot does real network work: it walks the tenant's base paths against $metadata and opens the ASMX session.

D. Windows host

The same tarball, run as a Windows service by WinSW — Windows cannot run node as a service by itself. Windows Server 2019 or later, with Node.js 22 or later installed for all users. Tested on Windows Server 2025 with Node 24 and WinSW 2.12.

  1. Configurator: pick Windows, then download install.ps1 into the folder. It carries the .env and ivanti-mcp.xml tabs inside it; download those only to read them.
  2. Edit install.ps1 in Notepad: in step 5 of the script, set IVANTI_BASE_URL to your tenant, and — for HTTP — MCP_PUBLIC_URL and TRUSTED_ORIGINS.
  3. Run it in an elevated PowerShell, from the folder. It asks for the Ivanti API key, then downloads and verifies the release and WinSW, locks down the settings, and installs and starts the service. 
    powershell -ExecutionPolicy Bypass -File .\install.ps1
  4. Check it — the script ends by printing {"status":"ok"}: 
    Get-Service ivanti-mcp
Get-Content "$env:ProgramData\ivanti-mcp\logs\ivanti-mcp.err.log" -Tail 20
Get-Content "$env:ProgramData\ivanti-mcp\secrets\bearer-token"   # bearer only — give it to your clients
WhereWhat
C:\Program Files\ivanti-mcpthe release, and WinSW as ivanti-mcp.exe with its ivanti-mcp.xml
C:\ProgramData\ivanti-mcpenv, secrets\ and logs\ — readable only by Administrators, SYSTEM and the service
  • It runs as LocalService, not WinSW’s default LocalSystem: it reads its settings and writes only its logs.
  • A configuration error restarts every 10 s. WinSW cannot spare exit 78 the way systemd does; the reason is in logs\ivanti-mcp.err.log.
  • Save settings and secrets as UTF-8 or ASCII. Windows PowerShell 5.1’s > writes UTF-16, which the server reads as a different value.
  • A tenant certificate from an internal CA needs --use-system-ca in the service’s arguments (Node 22.15 or later): otherwise Node does not read the Windows certificate store.
  • On the Ivanti server itself, keep MCP_BIND=127.0.0.1, and put IIS in front for TLS if clients elsewhere need it.

How much memory it needs

About 117 MiB idle, plus ~60 KiB per open session — 176 MiB with 1,000 sessions held open.

The chart’s defaults fit: the 192Mi request holds even 1,000 idle sessions, and the 512Mi limit is headroom for sessions that are working. MCP_MAX_SESSIONS (default 100) caps the count; at the cap, the least recently used idle session is closed, and 503 comes only when every session is busy.

Four things that bite

  • The tenant hostname must resolve where the server runs. Split-horizon DNS can hand a container an address it cannot reach — pin it with --add-host, compose’s extra_hosts, the chart’s hostAliases or the host’s hosts file.
  • MCP_BIND=0.0.0.0 inside a container or pod — loopback there is the container’s own.
  • package.json must sit next to dist/, or the server refuses to start. A container that starts and exits is usually this.
  • The health check passes when HTTP is off — a stdio deployment has nothing to check.

Secrets

Every secret also takes a _FILE form (BEARER_TOKEN_FILE, IVANTI_API_KEY_FILE); setting both is an error. Prefer files anywhere but a laptop — the environment shows in docker inspect and kubectl describe pod.

The image runs as uid 65532, and a mounted file keeps its host ownership: a mode-600 secret you own is unreadable, and the server exits 78 with EACCES. Fix: chown 65532:65532 secrets/* && chmod 600 secrets/*. The Helm chart sets fsGroup, so this does not apply there.

06 — OAuth providers

The only door that carries a verified identity

Under bearer, everyone holding the token is the same anonymous caller. Under oauth the token says who, and the person a conversation is helping stops being a claim it makes about itself. Three settings usually do it; the difficulty is entirely in what each provider decides to put in the token.

The audience is not your URL, and this is the commonest reason OAuth “doesn’t work” here. The spec has clients send resource=<your MCP URL>, which reads as though aud will then contain that URL. No mainstream provider works that way. So OAUTH_AUDIENCE is set independently of MCP_PUBLIC_URL: it is a comma-separated list, the token's own aud may itself be an array, and a token is accepted when the two sets intersect. A verifier written to the spec's literal wording rejects every real token.

ProviderWhat actually lands in audThe thing that will catch you
Entra IDdepends on the token versionv2: the API's client-id GUID · v1: the App ID URICannot be tested against localhost at all — see below
Zitadelthe client idToken type defaults to Bearer, which is opaque. Set Auth Token Type: JWT on the application
Oktathe authorization server's AudienceUse a custom authorization server — the org one issues opaque tokens
Keycloakthe client idDefault aud is account. Add an Audience mapper on the dedicated client scope
Auth0the API identifierOpaque unless a Default Audience is set tenant-side; its issuer ends in a trailing slash
JumpCloudthe client idNo dynamic registration — pre-register and pin the client id
Google—Not usable. Access tokens are opaque and there is no introspection endpoint

Nearly every failure is one of two shapes. An opaque token — the server answers “Access token is opaque, not a JWT”, and a JWKS verifier genuinely cannot inspect one: there is no header and no signature to check. That is always a provider setting, never a server one. Or the wrong audience, where the token is perfectly valid and simply was not minted for you. Decode it and read its real aud before changing anything else.

Entra is the exception, in four separate ways

It is the majority deployment and the one that behaves least like the others. None of these is something you can configure your way around.

  • Its audience depends on the token version you asked for. With requestedAccessTokenVersion: 2 the aud is the API's client id — a bare GUID. On v1.0 tokens it is the Application ID URI, api://<appId>. Both are correct; they are different strings, and putting the wrong one in OAUTH_AUDIENCE produces a valid token that this server refuses. Check the registration before assuming which you have.
  • It cannot be tested against a local server. Entra requires the resource to be a registered Application ID URI, and a conforming client separately insists the resource equals the endpoint it connected to. http://localhost:3000/mcp can never satisfy both — deploy to a public HTTPS name on a verified domain first, and then the App ID URI, MCP_PUBLIC_URL and the endpoint are one identical string. The api:// scheme takes a GUID that must match the app or tenant id, or an arbitrary string that must sit on a verified custom domain or the tenant's initial domain; api://<appId> is the recommended form.
  • Discovery only resolves on the third probe. Its issuer carries a path (…/{tenant}/v2.0), and the two path-insertion forms answer 404 — only appending /.well-known/openid-configuration to the issuer works. An implementation that tries fewer candidates cannot reach Entra at all.
  • It publishes no code_challenge_methods_supported — alone among ten providers measured here — while supporting PKCE S256 in practice. The spec says a client MUST refuse to proceed when that field is absent, so whether a given client tolerates it is decided on the client side and cannot be fixed from this end.

One app registration is enough: it can expose the API and act as the client. And if Custom domain names refuses to verify while your DNS is demonstrably correct, the domain is almost certainly claimed by another Microsoft tenant — often an unmanaged one created when somebody signed up for a free service using an address at that domain. That is a takeover case, not a DNS problem.

What to set

Discovery is the default: give it the issuer and the authorization-server metadata is fetched at startup, in the spec's probe order.

AUTH_MODE=oauth
OAUTH_ISSUER=https://login.microsoftonline.com/<tenant-id>/v2.0
OAUTH_AUDIENCE=<the API's client id, for a v2.0 token>

# Optional. Setting it skips discovery entirely — which is what you want when a
# provider publishes its metadata somewhere the spec's probe order does not look.
OAUTH_JWKS_URI=https://login.microsoftonline.com/<tenant-id>/discovery/v2.0/keys

# Which claim names the person. Entra sends preferred_username or upn, most
# others send email, and sub is opaque. Unset: email, but only with
# email_verified: true, then preferred_username, then upn. Set, it is used
# as-is — so name a claim users cannot edit in their profile.
OAUTH_IDENTITY_CLAIM=preferred_username

Assume the provider does not support dynamic client registration. Half of those surveyed do not, so a pre-registered client with a pinned client id is the documented path. Pinning also closes a Zitadel-specific trap: registration there creates a fresh application each time, which inherits the instance default of Bearer — so flipping one application to JWT lasts exactly until the next re-authentication makes another.

The redirect URI is not ours. It is where the provider sends the user back after login, so it belongs to the client application; this server neither hosts one nor ever sees it. MCP_PUBLIC_URL is always this server's own externally visible address. Confusing the two is the second-commonest setup failure — and a loopback redirect is not a “dev mode”, it is simply what a client running on somebody's own machine legitimately uses.

This server verifies tokens with JWKS and nothing else. It never mints a token, serves no registration endpoint and hosts no client metadata document: registration is strictly between the client and the authorization server. Token introspection is deliberately deferred rather than forgotten — across ten providers measured, jwks_uri was universal while introspection was absent on four, Entra included.

07 — Audience modes

full and enduser are different products

Chosen at startup; never mix audiences in one instance. Tool narrowing happens at registration, never inside a handler — an unregistered tool never appears in tools/list, so the model cannot call it at all.

 fullenduser

The act_as rows are the ones that catch people out. Without impersonation, anything Ivanti resolves "for the current user" — a saved search called “My Incidents”, an approval queue, an assignment — answers for the service account, not for whoever is chatting; with it, it answers for the person. Call act_as once per conversation to say who you are helping — in both modes it is the first call, and every other tool refuses until it succeeds. Under AUTH_MODE=oauth the token already names the person, so the first call pins them without being asked, and the model is not told to ask.

Name quick actions, never pattern-match them. They are the tenant's own text and a tenant renames them freely. An admin key sees every action the tenant defines, including escalation notifications and analyst-only composites — read them off list_quick_actions in full mode and copy the handful an end user should have.

A shared token grants its whole tool surface to everyone who can use it. Size the audience to the surface: pair a widely-shared bearer token with MCP_MODE=enduser.

08 — Impersonation

Signing in as the person

By default the server works as one API user, and act_as only says who “my” means. Given a ConfigDB key, act_as opens a real Ivanti session as that person instead. Optional, and off by default: set neither setting and nothing changes.

Then it really is them. With IVANTI_CONFIG_URL and IVANTI_CENTRAL_CONFIG_API_KEY set, act_as opens an Ivanti session as that person and Ivanti applies their own access — a self-service role sees only its own records, where the same request as an analyst sees them all — and a ticket they raise carries their name in CreatedBy rather than the service account’s.

Every surface follows the person: records, forms, pick lists, quick actions, and a service request with a file attached — measured, the request and its attachment both carry the person’s name in CreatedBy. What stays on the service account does so because it describes the tenant rather than the person: the schema, the admin catalog, the person directory. And the server’s own checks still run — the object gate and the ownership rules — because a second, independent line is worth keeping even where Ivanti draws the first.

If the session cannot be opened, the call is refused rather than quietly answered as the service account: being told the wrong person’s data is yours is worse than being told nothing.

When the session dies

An impersonated session ends without saying so. It lapses or the tenant evicts it, and every later call as that person answers 401. Re-opened once for the same login. A read is retried on the new session; a write is reported rather than repeated, because part of it may already have gone through. It never falls back to the service account.

10 — Reference docs

Six documents, fetched on demand

Served as MCP resources rather than baked into tool descriptions. Descriptions carry what is dangerous not to know; resources carry what is expensive to repeat — and cost nothing until something reads them.

11 — What a session costs

Where the context window goes

What the server costs a model’s context window, in three parts.

The standing cost, paid once per session

The server’s instructions and its tool list — every tool’s description and arguments — arrive before the model has asked anything, and are sent again with every new conversation. An enduser deployment registers fewer tools, so it sends less.

On demand — paid only if something reads it

Reference material lives in MCP resources rather than in the tool descriptions precisely so it is not part of that standing cost. A model fetches one only when it needs it, and most sessions fetch none.

Per call — the part that can ruin a window

Response size dwarfs everything above, and it is the one term you control per call.

A default page of twenty-five full records can cost several times the entire tool list, from a single list_records — a full Ivanti record carries every field its object has. That is why rows default to a compact field set and the response tells you which one it used; asking for fields explicitly is cheaper still.

12 — Limits

What it will not do

Two different things get confused with each other: a limit you must design around, and a door deliberately closed. They are separated here, and the closed ones carry their reason — a refusal without one is indistinguishable from an oversight.

Known limits

LimitWhat it means in practice
Opaque access tokens are refusedVerification is JWKS only. Google is unusable — its access tokens are opaque and it publishes no introspection endpoint. Zitadel, Okta and Auth0 each issue opaque tokens until a provider-side setting is changed; see section 06.
Entra publishes no code_challenge_methods_supportedAlone among ten providers measured, while supporting PKCE S256 in practice. The spec says a client MUST refuse to proceed when that field is absent, so whether it works is decided in the client and cannot be fixed here.
Entra cannot be exercised against a local serverIt requires the resource to be a registered Application ID URI; a conforming client requires it to equal the endpoint. http://localhost satisfies neither, so Entra work starts at a public HTTPS name on a verified domain.
HTTP sessions live in memoryOne replica. initialize carries no session id, so nothing can route a session back to the pod that minted it; scale out and roughly half of every conversation's requests reach a pod that has never heard of the session — which presents as intermittent client bugs.
Protocol 2025-11-25The MCP protocol revision this server speaks. A client that needs a newer revision's features will not find them here, whatever the specification says.
Attachments are capped at 2 MBUploads travel as base64 in a tool call, so the bytes cross the model's context twice. A larger file is refused rather than silently truncated. Reading one is capped too, and judged before a byte is fetched: an image at 1 MB, any other file at 5 MB, and a format no model can read is refused by its name.

Decided against

These are not gaps. Each was considered, tested where testable, and turned down for a reason that still holds.

Not plannedBecause
Several tenants in one processThe process boundary is a better fence than code: a tenant cannot leak across a boundary that does not exist in the first place. It would also put a tenant argument on all forty-one tools, where forgetting it once is a silent write to the wrong tenant. Staging, UAT and production are three deployments. Revisit if per-tenant deployments ever cost more than the isolation is worth — the opposite of the handful-of-environments case this was decided against.
Per-user Ivanti API keysNot provisionable at tens of thousands of employees.
A read-only gate for productionProduction is where the work happens. A switch that makes the useful deployment useless gets turned off.
A roles and permissions system in the serverOnly oauth could feed it a real identity, and the MCP annotations plus the client's own approval flow already cover the ground.

Startup exits 78Incomplete or unsafe configuration. Every problem is listed at once — fix them all. the token carries no claim naming the personUnder oauth: the token has no preferred_username or upn, and its email is not marked email_verified: true — an unverified address is never used. Set OAUTH_IDENTITY_CLAIM to a claim your users cannot edit.
MCP_PUBLIC_URL must not end with a trailing slashThe resource identifier is compared verbatim against the token audience.
Client keeps registering new appsIt is using dynamic client registration. Pin it with --client-id — and a running client reads its config at startup, so restart it.
Everything looks right, still 401Cached credentials from before the fix. Clear the client's stored authentication and re-authenticate.
Too many active sessions, and none has been idle long enough to closeA 503 on initialize: every session under MCP_MAX_SESSIONS had traffic in the last minute or has a request in flight, so none could be displaced. Retry-After says when one could. Raise the cap if that is the real load.
whether it was applied is unknownA write got no answer — it outlasted IVANTI_WRITE_TIMEOUT_MS, or a gateway answered 502 or 504. It may have been stored: check the record before repeating it. If such writes keep turning out to have taken effect, raise the write timeout.
A Windows service restarts every 10 sA configuration error: the server exits 78, and WinSW restarts anything that fails. The reason is in C:\ProgramData\ivanti-mcp\logs\ivanti-mcp.err.log.
Startup fails with unable to get local issuer certificate or self-signed certificate in certificate chainThe tenant’s certificate comes from a CA Node does not bundle — usually an internal one. Add --use-system-ca (Node 22.15 or later) so Node trusts the host’s certificate store, or point NODE_EXTRA_CA_CERTS at the CA’s PEM file.
A tool is missing from tools/listEither the mode does not register it, or the API key cannot reach what it needs. The startup log lists every tool this key reaches.

Raise the log level to debug for one line per MCP request — method, tool, session and the authenticated subject — and one per Ivanti request: path, query, status, duration, and Ivanti's own error body when it fails, each stamped with the tool call that caused it. debug carries personal data (a filter names people): turn it on to diagnose, not as a standing setting. Tool arguments and the values of a write are never logged — a write's audit line names only the record it was aimed at, by id — and an asserted identity is never logged as though it were a fact.

At info every tool call also writes a tool finished line — outcome, sizes, Ivanti requests.

Tool descriptions, arguments and annotations are the ones the server sends a client. Logs go to stderr as structured JSON; under stdio, stdout carries the MCP stream itself.
